# Native S3 acceptance fixtures

These flows require an installed iOS build, Maestro and a device-reachable, disposable S3 test destination. They preserve app state deliberately. Run each flow separately after preparing its fixture; do not run this directory as an unconfigured smoke suite. Use test-only credentials and a deterministic provider, never private conversations or a production bucket. A missing fixture is a setup failure, not a passing scenario. No fixture service or device execution is supplied by these YAML files.

Seed conversations using the schema in `src/storage/schema.ts` and the normal `conversations/<id>.json` and `manifest.json` contracts. Install local fixture files in the app's private conversation storage with matching local manifest entries before launching. Configure protected settings through the app. Each conversation has one user message and one successful assistant response, an empty draft and a valid UTC `updatedAt`; use stable distinct IDs. Reset local sync state and the disposable destination between scenarios. Keep initial local and remote bytes for recovery verification. Verify objects with a backend that enforces conditional writes; npm s3rver cannot establish that guarantee.

| Flow                | Required initial fixture                                                                                                                                                                                                        | Expected device behavior                                                                                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `startup.yaml`      | Local title `Sync local fixture`, response `Local fixture response`; remote-only title `Sync remote fixture`, response `Remote fixture response`; reachable S3                                                                  | Both titles appear, remote transcript opens without restart and remains available after relaunch.                                                                                                |
| `offline.yaml`      | Local fixture as above; complete S3 settings pointing to an unreachable test endpoint                                                                                                                                           | History failure exposes retry; local transcript and draft remain usable after retry. Check destination request traces show no provider request.                                                  |
| `response.yaml`     | Empty local history; reachable S3; deterministic provider returns `Fixture response one` for `Sync response fixture` and `Fixture response two` for `Sync edited fixture`                                                       | Completed response and edited response render; only the edited response remains after relaunch.                                                                                                  |
| `hold.yaml`         | Same ID on both sides with title `Sync held fixture`, equal timestamps, different response texts `Local fixture response` and `Remote fixture response`                                                                         | Hold survives relaunch; chosen transcript remains and hold disappears across relaunch. Run independently for both choices.                                                                       |
| `active-draft.yaml` | Local title `Sync active fixture`, response `Local fixture response`; newer remote same ID with response `Remote fixture response`; test proxy delays the conversation GET until the device has entered `Unsaved fixture draft` | Newly saved draft and local transcript survive incoming revision and relaunch with a durable hold. Release the GET only after draft entry; failing to control this barrier invalidates the test. |

Run from the repository root, for example `maestro test tests/e2e/sync/startup.yaml`. For the remote conflict choice, reset fixtures then run `maestro test -e CHOICE="Use remote" -e EXPECTED_RESPONSE="Remote fixture response" tests/e2e/sync/hold.yaml`.

For malformed repair, reset fixtures with a valid local `Sync held fixture` and a malformed remote object at the same name. Save the exact malformed bytes. Run `maestro test -e HOLD_MESSAGE="An S3 conversation needs repair. Its original data will be preserved." -e CHOICE="Repair from local" tests/e2e/sync/hold.yaml`. Afterward verify the private recovery file contains the exact original bytes and that the repaired remote object and manifest match the local conversation.

Device assertions alone do not prove transfer. After `response.yaml`, verify remote conversation messages contain the edited prompt and second response, the remote manifest metadata matches, and the provider trace contains exactly two requests. Capture requests during streaming to verify chunks do not trigger completion uploads. Repeat with an upload-failing test proxy: verify `Saved on this device. Couldn’t save to S3.`, restore connectivity, tap `Retry saving to S3`, then verify latest remote bytes and no new provider request. This failure transition is a manual fixture-controlled extension, not automated by the response flow.

After each conflict choice, verify the displaced revision in private recovery storage, the chosen remote conversation and manifest, a new timestamp later than both inputs, and unchanged unrelated objects. For startup, keep S3 blocked initially and verify local history renders before releasing the proxy. Also exercise unchanged active work becoming idle, stopped/error responses, process termination during queued writes, pending deletion, and destination/credential switches using the archived spec's acceptance scenarios. These lifecycle and backend observations remain manual checks; the flows do not claim full feature acceptance.

No iOS acceptance has been executed in the Linux development environment: `maestro` and `xcodebuild` are unavailable. YAML inspection and automated component tests do not substitute for running these flows with the specified fixtures.
